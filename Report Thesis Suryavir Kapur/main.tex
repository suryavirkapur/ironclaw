\begin{abstract}
Large Language Models (LLMs) increasingly act as agents that perform complex,
multi-step workflows. When no purpose-built capability exists, an agent can
either author the required logic inline on every request or synthesize a
task-specific tool once and reuse it. Reuse may improve long-horizon software
development and data-processing work, but executing synthesized code in an
ordinary process creates significant security risk. This dissertation presents
IronClaw, an autonomous agent platform that combines dynamic tool synthesis with
strictly isolated Firecracker microVMs. IronClaw separates the trusted host
daemon, which manages agent policy, context, and lifecycle, from a guest runtime
that executes generated code behind a hardware-virtualization boundary.

The evaluation methodology assesses whether registering and reusing dynamically synthesized tools improves utility relative to authoring the required logic inline on every request. Security and performance are evaluated separately by comparing micro-VM isolation with process-level execution of agent-generated code. The utility experiments use deterministic data-transformation and software-engineering tasks; the security protocol uses red-team payloads designed to attempt host escape or resource exploitation; and the systems protocol measures latency, CPU use, and memory overhead.

The utility experiments confirm that the benefit is real but bounded and extends beyond SQL. On repetitive workloads, dynamic synthesis reduced billed input tokens by 53.4\% for SQL query synthesis, 61.4\% for JavaScript parser synthesis, and 53.6\% for repository configuration compliance, relative to generic capabilities with no synthesis. Both conditions achieved 100\% correctness, while dynamic synthesis required fewer model steps in all three domains. On mixed workloads the same mechanism was net-negative because creation overhead was not amortized. In the security evaluation, all five host-resource attacks succeeded under process execution and none succeeded inside Firecracker. This isolation carried a 6.08-second median cold start, a 6.62-second median recovery, and 72{,}672\,KiB of host resident memory for a 512\,MiB-configured guest. H2 is therefore partially supported: containment is demonstrated for the payload suite, but low-latency initialization remains unproven until snapshot restore is implemented and measured.
\end{abstract}
