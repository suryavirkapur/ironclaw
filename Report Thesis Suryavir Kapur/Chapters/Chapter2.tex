\section{LLM Agents and Tool Use}
LLM agents extend language models by allowing them to call external tools,
maintain task state, and decompose goals into multi-step plans. Tool use improves
reliability because the model can delegate exact computation, file operations,
search, or program execution to deterministic systems. ReAct-style prompting
demonstrated that interleaving reasoning traces with actions can improve
interactive task solving \cite{yao2023react}. Toolformer showed that language
models can learn to decide when external API calls are useful
\cite{schick2023toolformer}. Generative Agents demonstrated memory, reflection,
and planning loops for believable software agents \cite{park2023generative},
while Voyager showed how an LLM agent can accumulate executable skills in an
open-ended environment \cite{wang2023voyager}.

Despite these advances, many deployed agents still depend on fixed registries of
tools selected before the task starts. A fixed registry simplifies auditing but
prevents the agent from creating missing utilities at runtime. Dynamic tool
synthesis generalizes tool use by allowing the agent to generate small programs
for task-specific transformations, tests, or integrations.

\section{Dynamic Tool Synthesis}
Dynamic tool synthesis is useful when tasks require code that is difficult to
predict in advance, such as converting unfamiliar file formats, aggregating
benchmark outputs, validating configuration variants, or generating
domain-specific checks. The agent writes code, executes it in an isolated
environment, observes the output, and decides whether to revise or reuse the
tool. The challenge is that generated code is untrusted by default. It may be
incorrect, excessive in resource use, or influenced by adversarial instructions
embedded in external content.

\section{Sandboxing and Isolation}
Traditional sandboxing techniques include language-level restrictions,
process-level privilege dropping, containers, seccomp filters, and namespaces.
These controls reduce the attack surface but still share the host kernel. A
kernel vulnerability or misconfiguration can turn a process-level boundary into a
host compromise. MicroVMs provide a stronger boundary by running guest workloads
inside hardware-assisted virtualization while retaining low startup overhead
compared with general-purpose virtual machines. This design follows the classic
virtual-machine monitor goal of providing equivalent execution, resource
control, and efficiency as formalized by Popek and Goldberg
\cite{popek1974formal}.

\section{Fundamentals of Sandboxing}
Sandboxes are systems where code is executed in an "environment" (a sandbox) with restrictions on what it can do. These restrictions include limiting file access, restricting network activity, constraining cpu \& memory usage, restricting system calls, and limiting execution time.

Agent generated code should never be treated as a convenience item, but as a required security mechanism. The model could produce code that is syntactically correct but semantically dangerous. In addition, the model could take malicious instructions from outside the system. As such, the sandbox must consider all code produced by the model to be malicious regardless of whether the end-users' requests were benign.

\section{Processes, Containers, and Virtual Machines}
A normal process is isolated from other processes by the operating system's
memory management and permission model. This is useful, but the process still
uses the same host kernel. If the process can exploit a kernel bug, abuse a
misconfigured permission, or access an overly broad mount, the host may be
affected.

Containers add namespaces, control groups, capabilities, and filesystem layering
around processes. They are efficient and practical for packaging, but they are
not a complete hardware boundary because the containerized workload still shares
the host kernel. This matters for IronClaw because generated tools are not merely
ordinary application code; they are untrusted programs created at runtime.

A virtual machine provides a stronger boundary by running a guest operating
system on virtualized hardware. The guest has its own kernel, memory view,
devices, and process tree. The host kernel does not directly execute guest
system calls. Instead, privileged guest operations are mediated by a hypervisor
or virtual machine monitor. This separation reduces the blast radius of
untrusted code because a guest compromise does not automatically become a host
compromise. Xen is a canonical example of a virtual machine monitor designed to
run multiple commodity operating systems safely on shared hardware
\cite{barham2003xen}.

\section{How Virtual Machines Execute on the CPU}
Modern CPUs include hardware virtualization extensions, such as Intel VT-x and
AMD-V, that allow a hypervisor to run guest code efficiently. Intel's
architecture manuals describe the VMX root and non-root modes used to enter,
run, exit, and resume virtual machines \cite{intel2025sdm}. In a simplified
view, the CPU has two relevant execution modes: a host-controlled mode for the
hypervisor and a guest mode for the virtual machine. The guest executes most
ordinary instructions directly on the CPU, so a virtual machine is not simply an
emulator interpreting every instruction.

When guest code performs a sensitive operation, such as configuring privileged
CPU state, accessing certain devices, or executing an instruction that the
hypervisor has chosen to intercept, the CPU performs a VM exit. Control returns
to the hypervisor, which decides how to handle the operation. After the
operation is handled, the hypervisor resumes the guest with a VM entry. This
exit-and-entry mechanism lets ordinary computation run near native speed while
keeping privileged operations under host control. Empirical work comparing
software and hardware techniques for x86 virtualization shows that the cost of
VM exits, page-table activity, and I/O paths is central to virtualization
performance \cite{adams2006comparison}.

Memory isolation is provided through hardware-assisted address translation. The
guest operating system believes it controls physical memory, but those guest
physical addresses are mapped to host physical pages by the hypervisor using
mechanisms such as Extended Page Tables on Intel processors or Nested Page
Tables on AMD processors. This prevents the guest from directly reading or
writing arbitrary host memory.

\section{MicroVMs}
A microVM is a virtual machine designed with a deliberately small device model
and minimal management surface. It keeps the stronger hardware virtualization
boundary of a VM while reducing the startup time and attack surface associated
with traditional general-purpose virtual machines. This makes microVMs suitable
for short-lived, isolated workloads such as serverless functions and
agent-generated tools. Firecracker is a production example of this approach,
designed specifically for lightweight virtualization in serverless applications
\cite{agache2020firecracker}.

In IronClaw, a microVM can be created for a tool execution or task session, run
the generated code, return bounded output, and then be discarded. This ephemeral
model helps prevent persistence, cross-tool contamination, and accidental reuse
of compromised state.

\section{Firecracker MicroVMs}
Firecracker is a lightweight virtual machine monitor designed for secure,
multi-tenant workloads \cite{agache2020firecracker}. It provides a minimal device model and
supports fast startup, making it suitable for short-lived isolated tasks. In
IronClaw, Firecracker is used to run agent-generated code in an ephemeral guest
environment. This design isolates tool execution from the host daemon and allows
the host to destroy or recreate the guest runtime after each session.

\section{Evaluation Benchmarks}
Complex software engineering benchmarks such as SWE-bench measure whether agents
can reason over real repositories and produce correct fixes \cite{swebench}.
IronClaw's evaluation adapts this style of benchmark by focusing on tasks where
tool creation can plausibly help: parsing outputs, running targeted checks,
transforming data, and repeatedly validating results.
