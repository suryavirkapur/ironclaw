\chapter{Conclusion and Future Work}
\label{Chapter6}
\lhead{Chapter 8. \emph{Conclusion and Future Work}}

\section{Contributions}
This research provides a practical architecture that integrates dynamic tool synthesis into micro-VM isolation. The first contribution is a boundary in which agent-generated code can be measured, destroyed, and replicated. The second contribution is the utility evaluation of Chapter~\ref{ChapterEval}: across three repetitive domains, dynamic synthesis reduced billed input tokens by 53.4\%, 61.4\%, and 53.6\%, respectively, while preserving 100\% correctness and reducing model steps. On mixed workloads, creation overhead was not amortized and synthesis was net-negative. The third contribution is the security and performance evaluation of Chapter~\ref{ChapterH2}. All five host-resource attacks succeeded under ordinary process execution and none succeeded inside Firecracker. The measured cost was a 6.08-second median cold start, 6.62-second median recovery, and 72{,}672\,KiB host resident memory for a 512\,MiB-configured guest.

\section{Limitations}
The utility evaluation uses one model, three synthetic domains, scripted requests, and one measured run per condition, so effect sizes may vary with other models, prompts, and real workloads. It identifies the direction and boundary of the effect, but not a universal numeric break-even point between three and six repetitions. The H2 evaluation uses one host and five non-destructive payloads against an unisolated process baseline. It does not cover network policy, kernel or VMM fuzzing, side channels, disk exhaustion, or stronger software sandboxes. Passing the suite demonstrates containment of those defined resources; it cannot prove the absence of every vulnerability.

\section{Future Directions}
There are four priority areas for extending IronClaw. First, snapshot creation and restore should be implemented and measured against the sub-500\,ms resume target; the present six-second cold boot is unsuitable for per-request VM creation. Second, TAP-layer network allow-lists and stronger CPU, memory, time, disk, and output enforcement should be completed and red-teamed. Third, the benchmark suite should include real codebases, additional models, repeated trials, and more reuse frequencies, while synthesized tools and their policies should be cached across sessions. Finally, the security suite should add fuzzing, kernel/VMM instrumentation, side-channel analysis, disk exhaustion, concurrency, and comparisons with namespaces, seccomp, containers, and WebAssembly sandboxes.

\section{Conclusion}
Ultimately, dynamic tool synthesis is a natural extension of the ability for autonomous agents to create new capabilities at runtime. H1 shows that, relative to no synthesis, dynamic tools preserve correctness while substantially reducing steps and token use when a capability is repeatedly reused, but impose a net cost when reuse is sparse. H2 shows that Firecracker contained every evaluated host-resource attack, unlike ordinary process execution, but imposes material cold-start and memory overhead. IronClaw is therefore viable today for long-lived isolated agent sessions; snapshot restore and stronger network/resource policy are required before claiming low-latency per-request isolation.
